## 🔄 部署方式对比

### 方式一：传统脚本部署

**流程**：
```
本地构建 → SCP上传 → SSH登录 → 执行脚本 → 手动验证
```

**优点**：
- ✅ 简单直接
- ✅ 学习成本低
- ✅ 适合小型项目

**缺点**：
- ⚠️ 需要手动操作
- ⚠️ 容易出错
- ⚠️ 部署耗时较长

**文档**：[快速部署指南.md](./快速部署指南.md)

---

### 方式二：CI/CD自动化部署 ⭐（推荐）

**流程**：
```
Git Push → 自动测试 → 自动构建 → 自动部署 → 健康检查
```

**优点**：
- ✅ 全自动化
- ✅ 快速可靠
- ✅ 版本可追溯
- ✅ 易于回滚

**缺点**：
- ⚠️ 初期配置稍复杂

**文档**：
- 配置：[GitHub_Secrets配置指南.md](./GitHub_Secrets配置指南.md)
- 使用：[CICD使用指南.md](./CICD使用指南.md)

## 🆘 常见问题

### Q1: 应该选择哪种部署方式？

**A**: 推荐路径：
- **首次上线**: 使用传统部署快速验证系统
- **系统稳定后**: 立即切换到CI/CD自动化部署

### Q2: CI/CD配置难吗？

**A**: 
- 初期配置需要5-10分钟
- 跟随[GitHub_Secrets配置指南.md](./GitHub_Secrets配置指南.md)逐步操作
- 一次配置，永久受益

### Q3: 如何快速回滚？

**A**: 
- 传统部署：执行`./backup-restore.sh`
- CI/CD部署：`git revert` + `git push`（3分钟完成）

### Q4: 部署失败怎么办？

**A**: 
1. 查看GitHub Actions日志（CI/CD）
2. 查看服务器日志：`docker logs -f msdsbackend-prod`
3. 参考[CICD使用指南.md](./CICD使用指南.md)故障排查章节

